# Spine Pair Review — AI-StudyBuddy

## Overall verdict
The spine pair is a usable contract. Every `{path.to.token}` reference in DESIGN.md resolves, every hex is defined, all three PRD journeys have full Key Flows, and the user-approved scope overrides are listed clearly in "Scope Changes vs PRD". Nothing is critical. The gaps that matter are states downstream builders would otherwise have to invent: the Mistake Review start/loading/failure path, the create-account and password-reset states (including the PRD's FR-1 duplicate-email rule), and what happens when a Google sign-in uses an email that already has an email account. Second-order issues: component names drift between sections, DESIGN.md carries behavior rules that duplicate EXPERIENCE.md, and about 15 behavioral "[ASSUMPTION: … not decided]" tags sit outside Open Questions.

The "All cleared" save failure appears only in the State Patterns table. - **low** Flow 5 (Flashcards) has no failure line for generation failure or the too-little-material case after start. (EXPERIENCE.md Key Flows › Flow 5). *Fix:* add one failure line pointing at the Generating › Failure pattern.
- **low** FR-3 (password reset) and FR-5 (rename) have no flow. They are not UJs, so this is acceptable. FR-3 also has no state coverage (see §4). (EXPERIENCE.md IA row "Password reset"). *Fix:* none needed for flows. Cover FR-3 in State Patterns.

## 2. Token completeness — adequate
Checked mechanically. The DESIGN.md frontmatter was parsed and every `{group.key}` reference in both files was resolved against it: 59 distinct references in DESIGN.md, all resolve. In EXPERIENCE.md, 9 references; 7 resolve, and the other 2 are the illustrative `{colors.x}` / `{typography.x}` in the intro. All 19 color tokens are valid 6- or 8-digit hex. Component `extends` targets (`button-ghost`, `modal-dialog`) exist. V1 is dark-only by decision, so no light/dark pairs are expected. Contrast was recomputed. The text pairs match the logged numbers. `on-primary` on `error` measures 5.68:1 (the spine says "about 5.7", not logged).
### Findings
- **medium** Contrast targets cover text only. WCAG 2.2 AA 1.4.11 (non-text contrast, 3:1) is not stated, and `border-strong` (text at 14%) measures about 1.46:1 on `surface`. For some controls that border is the only visible edge: the unchecked checkbox in the remove file dialog, count-picker options, scope and History segments, ghost buttons, and text inputs. (DESIGN.md Colors › Contrast table; frontmatter `border-strong`, `remove-dialog.checkbox-border`). *Fix:* add a non-text contrast row. Raise the checkbox and input boundaries, for example with a dedicated `border-control` token at ≥3:1, or record a deliberate exception.
- **low** The `on-primary`-on-`error` ratio is marked "computed at distill, not logged". *Fix:* log 5.68:1 in the memlog and drop the qualifier.
- **low** Several literal dimensions bypass tokens: progress bar 4px, phone action/send buttons 56/52px, avatar 30px/56px, collapse button 28px, file-type tile 32px, 3px accent edges (used on 4+ components), footer 11px, thumbnail × 20px. (DESIGN.md frontmatter `progress-bar`, `phone-*`; Components prose). *Fix:* tokenize the repeated ones (`accent-edge-width: 3px`, avatar sizes) and leave one-offs literal.
- **low** "Disabled: reduced opacity" appears on 5 components (Button primary, Tool buttons row, Composer, Phone send button, danger confirm), but no opacity value or token is given. *Fix:* add one `opacity-disabled` value. If kept as a literal, check that disabled labels stay legible.
- **low** Some frontmatter values are not resolvable token strings: `'{colors.primary}, pulsing'`, `'hollow, {colors.text-muted}'`, and the non-spec `extends` key. A strict resolver will choke on them. *Fix:* split them into separate keys (`dot-style: pulsing`) or move them to prose.

## 4. State coverage — thin
Checked: every IA surface for empty, cold-load, loading/pending, error, focus, permission, and narrow-window states. File statuses, daily limits, generation, phone link, destructive actions, and the "newer surfaces" table are thorough. Several primary surfaces still lack the states story-dev will need.
### Findings
- **high** Mistake Review has no start, loading, or failure state. FR-18 generates fresh practice questions, but the Generating section and Progress steps cover only Quiz, Flashcards, and Summary. Nothing says what shows between "Start" and the first question, or what happens if that generation fails. (EXPERIENCE.md State Patterns › Generating; Component Patterns › Progress steps, Mistake Review session). *Fix:* add Mistake Review to the Generating table (progress steps or a short loading line) with a failure row (inline red + Try again, card count unchanged).
- **high** Create account and Password reset have no states. The PRD's testable FR-1 consequence ("an email already registered … sees a clear error") is missing. FR-3 states are also missing: reset link sent, link expired or invalid, password rules, success → login. (EXPERIENCE.md IA rows "Create account", "Password reset"; State Patterns › Errors covers sign-in only). *Fix:* add an "Account" state table covering duplicate email, field validation, reset requested (same message whether or not the email exists), expired link, and reset success.
- **high** Account identity across the two sign-in methods is undefined. Not covered: what happens when "Sign in with Google" uses an email that already has an email-and-password account (merge, link, or error; FR-1 allows one Account per email), what "Link Google account" does, and its states (already linked to another account, cancelled consent). This is load-bearing for architecture. (EXPERIENCE.md IA › Settings 1. Account; Component Patterns › Settings section, Google button; Notes for Architecture has no auth note). *Fix:* commit a rule (for example: same email → sign in to the existing Account and link Google automatically) and add a NOTE FOR ARCHITECTURE.
- **medium** Project home has no cold-load state, and chat has no pending-answer state (between Send and the grounded answer: thinking indicator, streaming or not, whether Send is disabled). Only History, menus, and dialogs have a "Loading…" treatment. (EXPERIENCE.md State Patterns › Project and chat). *Fix:* add rows for project cold-load and the in-flight chat answer, including the reduced-motion treatment.
- **medium** Leaving a Quiz or Flashcards session part-way is unspecified. "← Back to chat" is "always present", but nothing says whether a half-done quiz is saved, can be resumed, or appears in History, or whether mistakes already recorded stay (they should, per FR-12). Flashcards "Stop for now" has the same gap. (EXPERIENCE.md Component Patterns › Activity header, Flashcard). *Fix:* add a row: answered questions keep their recorded mistakes, and the partial run is (or is not) saved to History.
- **medium** Where the student lands after a destructive action is not specified: after deleting the open Project, after deleting the last Project (→ empty Projects page?), and after deleting the account (→ login with a confirmation?). Also unspecified: what happens to generation still running in a deleted Project. (EXPERIENCE.md State Patterns › Destructive actions). *Fix:* add a "Lands on" column.
- **low** Settings › Your data "Delete a project" hands off to the sidebar menu in an undecided way ([ASSUMPTION]), so that Settings row has no defined behavior. (EXPERIENCE.md IA › Settings 3). *Fix:* decide it, for example by listing Projects inline with a Delete action that opens the same dialog.
- **low** Session expiry (FR-2, 30 days) during use is not covered: redirect to login, and whether the current Project is kept as the post-login landing. *Fix:* one row in Errors.
