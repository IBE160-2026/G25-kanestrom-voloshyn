# Epic 1 Context: Get in: accounts, sign-in, and a runnable app

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Lay the foundation every later epic builds on. The grader can clone the repo and run the whole app locally in mock mode, with no paid key. A student can create an Account with email or Google, log in, stay signed in, log out, reset a forgotten password, and use the interface in English or Norwegian (bokmål) from the first screen. Epic 1 delivers the scaffold, the identity backend (profiles, verification, auth emails, the Supabase Auth adapter), the auth dependency that guards every later data endpoint, the design tokens, the i18n system, and the backend and frontend test setups that all later epics assume. Stories 1.1–1.5 are done; Story 1.6 (Google sign-in) remains, and Google OAuth is configured locally for it.

## Stories

- Story 1.1: Runnable app skeleton the grader can start locally
- Story 1.2: Switch the interface between English and Norwegian
- Story 1.3: Create an account with email and password
- Story 1.4: Log in, stay signed in, and log out
- Story 1.5: Reset a forgotten password
- Story 1.6: Sign in with Google

## Requirements & Constraints

- **Runnability:** `.env.example` → `.env`, `npx supabase start` (copy the printed local keys into `.env`; `npx supabase status` shows them again), `npx supabase db reset`, `docker compose up`. No API key, no paid calls. Backend tests: `uv run pytest`, always `LLM_MODE=mock`, against local Supabase. Frontend tests: `npm test` in `frontend/`, no backend needed.
- **Accounts:** sign-up takes first name, email, and a password of at least 8 characters. One Account per email, whichever method created it; a duplicate is refused. An automated test shows a 7-character password sign-up fails. Passwords are never stored or logged in plain text.
- **Email verification:** single-use link valid 24 h, resendable; a resend invalidates older links. Verification gates **only** Google linking; nothing else is blocked.
- **Login:** one generic failure message that never reveals whether the email exists. After login: the empty Projects page until Epic 2 adds Projects. Sessions last 30 days; logout ends the session at once and the old token is refused. After expiry, logging in again returns to the same page, with a signed-out message shown first.
- **Password reset:** every request gets the same reply; only Accounts with an email identity get mail. Links last 1 h, work once, and a newer link replaces older ones; expired/used/replaced links all show the same expired state with "Send a new link". After a reset the old password fails and every other session ends. Unverified Accounts reset the same way.
- **Google:** button hidden on Login and Create account when Google isn't configured (no keys, switch off); everything else still works. New Google email → new Account with Google first name and picture, landing on Projects. Matching **verified** email Account → Supabase's automatic identity linking is accepted: signed in and linked at once, no password step, no message; both methods then work. Matching **unverified** email Account → taken over: password stops working, all earlier sessions end, one-time notice; an automated test with seeded identities proves `user_auth` enforces this even without `after-sign-in`. An identity already linked elsewhere → `google_identity_in_use` ("already linked" error); cancelled consent → "Sign-in didn't work. Try again."; neither changes any Account. With Google linked, first name and picture come from Google and are read-only.
- **Language:** no saved choice → browser language, fallback English. Switchable before sign-in and persists across reloads; after sign-in it is saved to the Account and follows the student to other browsers. API errors render translated. Norwegian stays draft; final wording is accepted in Story 7.5, which doesn't block this epic.
- **Security:** never log passwords, tokens (including verification and reset tokens), or keys. Secrets only in `.env`; `.env.example` lists every variable name without a value. SMTP credentials, the Supabase secret key, and DB credentials stay backend-only.

## Technical Decisions

- **Scaffold:** `frontend/` from `npm create vite@9` (React, JavaScript, Vite 8); `backend/` as a uv project (Python 3.14), async FastAPI, one `psycopg_pool.AsyncConnectionPool`, plain SQL in `app/db/`, no ORM; `supabase/` with `config.toml` and `migrations/`; root `package.json` pins `supabase@2.122.0` exactly; Node ≥ 22.22.2 (24 ≥ 24.15 or 26) in `engines`. One multi-stage `Dockerfile` and a one-container `docker-compose.yml` reaching the host via `host.docker.internal`. One instance, one uvicorn worker.
- **Routing:** all API routes under `/api/`; unknown `/api/...` paths return the JSON error envelope with `404 not_found`; the SPA is served with an `index.html` fallback so deep links work; in dev, Vite proxies `/api`.
- **Runtime config:** `GET /api/config` returns only `{supabase_url, supabase_publishable_key, google_enabled}`; no build-time Supabase values or `VITE_*` secrets. `google_enabled` comes from the same `SUPABASE_AUTH_EXTERNAL_GOOGLE_ENABLED` variable that `config.toml` uses.
- **Mock-mode startup:** `APP_ENV=development`, no key, `LLM_MODE` unset → `mock` with a logged warning. `APP_ENV=production` fails startup when `LLM_MODE` is unset, or is `live` without `OPENROUTER_API_KEY` (AD-4). A test asserts no module outside `app/llm/` imports `openai`.
- **Supabase auth (`config.toml`):** `enable_confirmations = false` (verification is app-level), `minimum_password_length = 8`, `enable_manual_linking = true`, `otp_expiry = 3600`, Google `enabled = env(SUPABASE_AUTH_EXTERNAL_GOOGLE_ENABLED)` with client id/secret via `env()`, per-environment `site_url` and redirect URLs (`/auth/callback`, the reset route). Mailpit's SMTP port (54325) is enabled here.
- **Browser and Supabase:** `supabase-js` only in `frontend/src/auth/`, for sign-up, password login, `signInWithOAuth`/`linkIdentity`, logout, reading the token, completing a reset, and `updateUser({password})`; never `updateUser({email})`. All app data goes through `frontend/src/api/client.js`. After sign-up and every sign-in the SPA calls `POST /api/auth/after-sign-in`; after a completed reset, `POST /api/auth/after-password-reset`. `auth/` maps every login failure to one generic message.
- **Supabase Auth adapter:** `app/supabase_auth.py` is the only code that calls Supabase Auth over HTTP (token check, admin `generate_link`, admin user update/delete, identity unlink), using one `httpx2` client created in the lifespan (`storage.py` later shares it). No `supabase` Python SDK.
- **`user_auth` (`app/auth.py`)** is the only token parser for user routes. It (1) validates the token via `GET {SUPABASE_URL}/auth/v1/user` through `supabase_auth.py`: only a 401/403 means `unauthorized`; timeout, connection error, or 5xx → `auth_unavailable` (503), and the SPA keeps its session and shows the generic error; (2) looks up `session_id` in `auth.sessions`: missing → `unauthorized`, `created_at` NULL or older than `SESSION_MAX_AGE_DAYS` (30) → `session_expired`; (3) creates the `profiles` row idempotently; (4) enforces the Google takeover once: Google identity + `email_verified_at IS NULL` + `google_takeover_at IS NULL` → random password via admin API, delete every other session, set `google_takeover_at` and `notice_google_takeover`. The takeover commits in its own transaction before the route handler runs. It must work even if the SPA never calls `after-sign-in` (test with seeded identities). On `unauthorized`/`session_expired` the SPA signs out and keeps the intended route in `sessionStorage`.
- **Identity data:** `profiles` (`account_id` → `auth.users`, cascade) with `first_name`, `language`, `email_verified_at`, `google_takeover_at`, `notice_google_takeover`, `ui_prefs jsonb`, `last_project_id`, `privacy_notice_ack_at`. `email_verifications` stores hashed single-use tokens; link is `GET /api/auth/verify?token=`. `GET/PATCH /api/me` reads/writes the profile, including language. Schema changes only via SQL in `supabase/migrations/`.
- **Password reset:** `POST /api/auth/password-reset` always answers identically; for an email identity it calls admin `generate_link` (type recovery, no Supabase email) and sends the link itself.
- **Email:** only `mailer.py` sends auth mail, over SMTP with `aiosmtplib`, in `profiles.language`, falling back to the pre-sign-in language the SPA sends. Locally: Mailpit SMTP on port 54325 (enabled in `config.toml`, reached from the container via `host.docker.internal`); web UI at `localhost:54324`.
- **Transactions:** one pooled connection and transaction per request; services take `conn` and never commit. No Supabase admin call and no SMTP send inside an open write transaction: mail goes out after the commit, and a send failure is logged and never changes the response.
- **Errors:** `{"error": {"code", "params", "message"}}` with a matching HTTP status, mapped in `api/`. The SPA renders from `code` + `params` via the i18n catalogues and never shows `message`. Epic 1 codes: `unauthorized`, `session_expired`, `auth_unavailable`, `not_found`, `link_expired`, `email_not_verified`, `google_identity_in_use`.
- **Async:** routes, repositories, `supabase_auth.py`, and the mailer are `async`; pure helpers sync.
- **Frontend:** `frontend/src/styles/tokens.css` holds every DESIGN.md token as a custom property; components use only `var(--…)`; dark theme only. One CSS Module per component; no Tailwind or component library. `radix-ui` for focus-managed widgets (e.g. Account menu), `react-router` 8, bundled `@fontsource-variable/inter`, `lucide-react`. Strings come from `frontend/src/i18n/en.json` / `nb.json` via `react-i18next`, with plural forms.
- **Frontend tests:** Vitest + `@testing-library/react`, `jest-dom`, `user-event`, jsdom, all devDependencies in `frontend/`. `npm test` = `vitest run`, configured in `vite.config.js`, `globals: false`, one setup file `src/test/setup.js`. No backend, Supabase, or network: `api/client.js` and `auth/` are tested by stubbing `fetch` and `supabase-js`; every other test mocks those two modules. Use the real i18n catalogues through a shared render helper; never mock `react-i18next`.

## UX & Interaction Patterns

- **Login screen:** wordmark; tagline; "Sign in with Google"; email + password with "Log in"; "Forgot password?"; "Create account"; privacy line; EN | NO toggle. Compose from `mockups/key-login.html`; DESIGN.md wins on conflict.
- **Error line:** above the buttons, announced to assistive tech. Buttons stay active, the typed email stays, focus returns to the form. Bad login: "Wrong email or password."; failure or cancel: "Sign-in didn't work. Try again."
- **Create account:** first name, email, password, or Google; success lands on the empty Projects page. Errors in the Error line: duplicate "An account with this email already exists. Log in instead?" (Log in goes to Login); "Use at least 8 characters."; "Enter your first name."; "Enter your email."; "Enter a valid email address."
- **Other auth screens:** Password reset request ("Reset your password" · "Send link") → "If an account exists, we've sent a link"; new-password screen ("Choose a new password" · "Save password") → "Your password is changed. Log in with the new one."; bad link → "This link has expired" · "Send a new link". Verified link → "Your email is verified." Session expiry → "You've been signed out. Log in to continue." The language toggle appears on Login, Create account, and Password reset.
- **Verification email:** subject "Confirm your email for Study Buddy"; plain body: "Hi {name}," · "Confirm your email address by opening this link:" · the link · "The link works for 24 hours. You can use Study Buddy without confirming; you only need it to link a Google account." · "If you didn't create an account, you can ignore this email." Norwegian draft rows exist alongside; send in the Account's language.
- **Account menu:** top right on signed-in pages: "Welcome, {first name}" plus avatar (Google photo, or initials). Holds Language (English / Norsk, each in its own language) and an immediate Log out landing on Login; Settings arrives in Story 7.3. Below 1024 px it shows the avatar only. When there is no first name, the menu trigger's accessible name is "Account menu" (Norwegian draft: "Kontomeny").
- **Projects page (empty):** "Create your first project". The takeover notice "Your account now signs in with Google." reuses the Undo message component, with no action.
- **Copy:** every string, including API error messages, comes from the EXPERIENCE.md strings table (English plus draft Norwegian). Failures are stated briefly and calmly, never as technical codes.
- **Done for every story:** empty, loading, error, and narrow-window states; keyboard paths; reduced motion; WCAG AA contrast, 44×44 px targets, live regions; no hard-coded colours.

## Cross-Story Dependencies

- Story 1.6 builds on what 1.1–1.5 shipped: `/api/config`'s `google_enabled`, the `config.toml` Google block and `/auth/callback` redirect, `after-sign-in`, `profiles` (`google_takeover_at`, `notice_google_takeover`), `supabase_auth.py` admin calls, `user_auth`, and the Login / Create account screens. Settings' "Link Google account" (verification-gated `linkIdentity`) is Epic 7, not 1.6.
- Story 1.1 comes first: scaffold, `/api/config`, the error envelope, mock-mode tests, `tokens.css`, and `config.toml` underpin everything.
- Story 1.2 sets up i18n, API-error rendering from `code`/`params`, and the frontend test conventions every later screen reuses. Norwegian wording is accepted only in Story 7.5.
- Story 1.3 creates `profiles`, `after-sign-in`, verification, `mailer.py`, and `supabase_auth.py`, reused by Stories 1.5 and 1.6. Story 1.4's `user_auth` guards every data endpoint in Epics 2–7, and Story 1.6's takeover check lives inside it.
- Later epics extend this: Epic 2 adds Projects, landing on the last Project, and the privacy-notice acknowledgment; Epic 7 adds Settings (link Google, resend verification, change password), account deletion via `supabase_auth.py`, and the bilingual sign-off.
