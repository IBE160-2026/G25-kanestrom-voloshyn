# Epic 1 Context: Get in: accounts, sign-in, and a runnable app

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Lay the foundation every later epic builds on. The grader can clone the repo and run the whole app locally in test (mock) mode, with no AI key and no paid calls. A student can create an Account with email or Google, log in, stay signed in, log out, reset a forgotten password, and use the interface in English or Norwegian (bokmål) from the first screen. Epic 1 delivers the scaffold, the test-mode switch, the identity backend (profiles, verification, auth emails, the Supabase Auth adapter), the auth dependency that guards every later data endpoint, the design tokens, the i18n system, and the backend and frontend test setups that all later epics assume. Scope tiers: account creation, login, and test mode are Core and never cut. Password reset, Google sign-in, and the bilingual interface are Extensions. If time runs out, Google sign-in is third in the cut order (after phone upload and image text), and cutting it also removes the Google consequences in other stories.

## Stories

- Story 1.1: Runnable app skeleton the grader can start locally
- Story 1.2: Switch the interface between English and Norwegian
- Story 1.3: Create an account with email and password
- Story 1.4: Log in, stay signed in, and log out
- Story 1.5: Reset a forgotten password
- Story 1.6: Sign in with Google

## Requirements & Constraints

- **Runnability and test mode:** `.env.example` → `.env`, `npx supabase start` (copy the printed local keys into `.env`; `npx supabase status` shows them again), `npx supabase db reset`, `docker compose up`. With no AI key the app starts in test mode, sends no external AI request, and still enforces every limit; a production start without a key fails with a clear message. Backend tests: `uv run pytest`, always `LLM_MODE=mock`, against local Supabase. Frontend tests: `npm test` in `frontend/`, no backend needed.
- **Accounts:** sign-up takes first name, email, and a password of at least 8 characters. One Account per email, whichever method created it; a duplicate is refused. An automated test shows a 7-character password sign-up fails. Passwords are never stored or logged in plain text.
- **Email verification:** single-use link valid 24 h, resendable; a resend invalidates older links. Verification gates **only** Google linking. It never blocks normal use, password change, or reset.
- **Login:** one generic failure message that never reveals whether the email exists. After login: the empty Projects page until Epic 2 adds Projects. Sessions last 30 days; logout ends the session at once and the old token is refused. After expiry, logging in again returns to the same page, with a signed-out message shown first.
- **Password reset:** every request gets the same reply; only Accounts with an email identity get mail (a Google-only Account gets none). Links last 1 h, work once, and a newer link replaces older ones. Expired, used, and replaced links all show the same expired state with "Send a new link". After a reset the old password fails and every other session ends. Unverified Accounts reset the same way.
- **Google:**
  - The button is hidden when Google isn't configured (no keys, switch off), and everything else still works.
  - A new Google email creates a new Account with the Google first name and picture.
  - A matching **verified** email Account: the student is signed in and linked at once, with no password step and no linking message. Both methods then reach the same Account.
  - A matching **unverified** email Account is taken over: the student is signed in and linked, the old password stops working, every earlier session ends, and the student is told once (not on later logins). It must be enforced server-side even if the browser skips the follow-up call.
  - A Google identity already linked to another Account, or cancelled consent, changes no Account and shows an error. Both methods can be retried.
  - With Google linked, the first name and picture follow Google and are read-only.
- **Language:** with no saved choice the interface follows the browser language, falling back to English. It can be switched before sign-in and persists across reloads. After sign-in it is saved to the Account and follows the student to other browsers. API errors render translated. The Norwegian strings were signed off on 2026-11-16 and are binding. A new string follows the bilingual glossary and needs both reviewers' approval.
- **Security:** never log passwords, tokens (including verification and reset tokens), or keys. Secrets only in `.env`; `.env.example` lists every variable name without a value. SMTP credentials, the Supabase secret key, and DB credentials stay backend-only.

## Technical Decisions

- **Scaffold:** `frontend/` from `npm create vite@9` (React, JavaScript, Vite 8); `backend/` as a uv project (Python 3.14), async FastAPI, one `psycopg_pool.AsyncConnectionPool`, plain SQL in `app/db/`, no ORM; `supabase/` with `config.toml` and `migrations/`; root `package.json` pins `supabase@2.122.0` exactly; Node ≥ 22.22.2 (24 ≥ 24.15 or 26) in `engines`. One multi-stage `Dockerfile` and a one-container `docker-compose.yml` reaching the host via `host.docker.internal` (`extra_hosts: host-gateway`). One instance, one uvicorn worker.
- **Routing:** all API routes under `/api/`; unknown `/api/...` paths return the JSON error envelope with `404 not_found`; the SPA is served with an `index.html` fallback so deep links work; in dev, Vite proxies `/api`.
- **Runtime config:** `GET /api/config` returns only `{supabase_url, supabase_publishable_key, google_enabled}`; no build-time Supabase values or `VITE_*` secrets. `google_enabled` comes from the same `SUPABASE_AUTH_EXTERNAL_GOOGLE_ENABLED` variable that `config.toml` uses. No other app variable may use the `SUPABASE_AUTH_*` prefix, because the CLI reads those as config overrides.
- **Test-mode startup (AD-4):** `APP_ENV=development`, no key, `LLM_MODE` unset → `mock` with a logged warning. `APP_ENV=production` fails startup when `LLM_MODE` is unset, or is `live` without `OPENROUTER_API_KEY`. A test asserts no module outside `app/llm/` imports `openai`.
- **Supabase auth (`config.toml`, mirrored to Cloud):** `enable_confirmations = false` (verification is app-level), `minimum_password_length = 8`, `enable_manual_linking = true`, `otp_expiry = 3600`, Google `enabled = env(SUPABASE_AUTH_EXTERNAL_GOOGLE_ENABLED)` (default false) with client id and secret via `env()`, per-environment `site_url` and redirect URLs (`/auth/callback`, the reset route). Mailpit's SMTP port (54325) is enabled here.
- **Browser and Supabase:** `supabase-js` only in `frontend/src/auth/`, for sign-up, password login, `signInWithOAuth`/`linkIdentity` for Google, logout, reading the token, completing a reset, and `updateUser({password})`; never `updateUser({email})`. All app data goes through `frontend/src/api/client.js`. After sign-up and every sign-in (including Google) the SPA calls `POST /api/auth/after-sign-in`; after a completed reset, `POST /api/auth/after-password-reset`. `auth/` maps every login failure to one generic message.
- **Supabase Auth adapter:** `app/supabase_auth.py` is the only code that calls Supabase Auth over HTTP (token check, admin `generate_link`, admin user update and delete, identity unlink), using one `httpx2` client created in the lifespan (`storage.py` later shares it). No `supabase` Python SDK.
- **`user_auth` (`app/auth.py`)** is the only token parser for user routes:
  1. It validates the token via `GET {SUPABASE_URL}/auth/v1/user` through `supabase_auth.py`. Only a 401/403 means `unauthorized`; a timeout, connection error, or 5xx gives `auth_unavailable` (503), and the SPA keeps its session and shows the generic error.
  2. It looks up `session_id` in `auth.sessions`: missing → `unauthorized`; `created_at` NULL or older than `SESSION_MAX_AGE_DAYS` (30) → `session_expired`.
  3. It creates the `profiles` row idempotently.
  4. It enforces the Google takeover once: Google identity + `email_verified_at IS NULL` + `google_takeover_at IS NULL` → set a random password via the admin API, delete every other `auth.sessions` row, and set `google_takeover_at` and `notice_google_takeover`. The takeover commits in its own transaction before the route handler runs, so a later rollback can't undo the session deletes. `after-sign-in` is only a fast path for this check. Test it with seeded identities and no `after-sign-in` call.

  On `unauthorized`/`session_expired` the SPA signs out and keeps the intended route in `sessionStorage`.
- **Google linking:** for a verified email Account, Supabase's automatic identity linking is accepted. A Google identity already linked elsewhere → `google_identity_in_use`. Settings' "Link Google account" (`linkIdentity`, Epic 7) is offered only while `email_verified_at` is set. The backend re-checks after linking and removes a link made without verification through the admin API (`email_not_verified`).
- **Identity data:** `profiles` (`account_id` → `auth.users`, cascade) with `first_name`, `language`, `email_verified_at`, `google_takeover_at`, `notice_google_takeover`, `ui_prefs jsonb`, `last_project_id`, `privacy_notice_ack_at`. With Google linked, the first name and picture come from the Google identity data and are read-only. `email_verifications` stores hashed single-use tokens; the link is `GET /api/auth/verify?token=`. `GET/PATCH /api/me` reads and writes the profile, including language. Schema changes only via SQL in `supabase/migrations/`.
- **Password reset:** `POST /api/auth/password-reset` always answers identically. For an email identity it calls admin `generate_link` (type recovery, no Supabase email) and sends the link itself.
- **Email:** only `mailer.py` sends auth mail, over SMTP with `aiosmtplib`, in `profiles.language`, falling back to the pre-sign-in language the SPA sends. Locally this is Mailpit: SMTP on port 54325 (enabled in `config.toml`, reached from the container via `host.docker.internal`), web UI at `localhost:54324`.
- **Transactions:** one pooled connection and transaction per request; services take `conn` and never commit. No Supabase admin call and no SMTP send inside an open write transaction. Mail goes out after the commit, and a send failure is logged and never changes the response.
- **Errors:** `{"error": {"code", "params", "message"}}` with a matching HTTP status, mapped in `api/`. The SPA renders from `code` + `params` via the i18n catalogues and never shows `message`. Epic 1 codes: `unauthorized`, `session_expired`, `auth_unavailable`, `not_found`, `link_expired`, `email_not_verified`, `google_identity_in_use`.
- **Async:** routes, repositories, `supabase_auth.py`, and the mailer are `async`; pure helpers stay sync.
- **Frontend:** `frontend/src/styles/tokens.css` holds every DESIGN.md token as a custom property; components use only `var(--…)`; dark theme only. One CSS Module per component; no Tailwind or component library. `radix-ui` for focus-managed widgets (for example the Account menu), `react-router` 8, bundled `@fontsource-variable/inter`, `lucide-react`. Strings come from `frontend/src/i18n/en.json` / `nb.json` via `react-i18next`, with plural forms.
- **Frontend tests:** Vitest + `@testing-library/react`, `jest-dom`, `user-event`, jsdom, all devDependencies in `frontend/`. `npm test` = `vitest run`, configured in `vite.config.js`, `globals: false`, one setup file `src/test/setup.js`. No backend, Supabase, or network: `api/client.js` and `auth/` are tested by stubbing `fetch` and `supabase-js`, and every other test mocks those two modules. Use the real i18n catalogues through a shared render helper; never mock `react-i18next`.

## UX & Interaction Patterns

- **Login screen:** wordmark; tagline "Study from your own notes, with sources"; the Auth panel with the Google button, an "or" divider, and email + password with "Log in"; "Forgot password?"; "Create account"; privacy line; EN | NO toggle top right. Compose from `mockups/key-login.html`; DESIGN.md wins on conflict.
- **Google button:** full-width ghost button at the auth button height, "Sign in with Google" / "Logg inn med Google", in the Auth panel (Google button, "or" divider, email form) on Login and Create account. It is rendered only when `/api/config` reports `google_enabled`.
- **Error line:** above the buttons, announced as an alert. Buttons stay active, the typed email stays, and focus returns to the form. Bad login: "Wrong email or password." Google failure or cancel: "Sign-in didn't work. Try again." / "Innloggingen fungerte ikke. Prøv igjen." Google identity in use (`google_identity_in_use`; the strings table's only "already linked" string): "This Google account is already linked to another Study Buddy account." / "Denne Google-kontoen er allerede koblet til en annen Study Buddy-konto."
- **Create account:** first name, email, password, or Google; success lands on the empty Projects page. Errors in the Error line: duplicate "An account with this email already exists. Log in instead?" ("Log in" goes to Login); "Use at least 8 characters."; "Enter your first name."; "Enter your email."; "Enter a valid email address."
- **Other auth screens:** Password reset request ("Reset your password" · "Send link") → "If an account exists, we've sent a link"; new-password screen ("Choose a new password" · "Save password") → "Your password is changed. Log in with the new one."; bad link → "This link has expired" · "Send a new link". Verified link → "Your email is verified." Session expiry → "You've been signed out. Log in to continue." The language toggle appears on Login, Create account, and Password reset.
- **Auth emails:** verification subject "Confirm your email for Study Buddy"; reset subject "Reset your Study Buddy password"; plain bodies as in the strings table, sent in the Account's language.
- **Account menu:** top right on signed-in pages: "Welcome, {first name}" plus avatar (the Google photo for Google Accounts, otherwise initials). It holds Language (English / Norsk, each in its own language) and an immediate Log out that lands on Login; Settings arrives in Story 7.3. Below 1024 px it shows the avatar only. With no first name, the trigger's accessible name is "Account menu" / "Kontomeny".
- **Projects page (empty):** "Create your first project". The one-time takeover notice "Your account now signs in with Google." / "Kontoen din logger nå inn med Google." reuses the Undo message component with no action (polite live region, 6 s, persists on hover or focus).
- **First Google sign-in flow:** Login (in the browser's language) → "Sign in with Google" → consent → the empty Projects page greeted by first name. A matched verified Account shows no extra message; a takeover adds the one-time notice.
- **Copy:** every string, including API error messages, comes from the EXPERIENCE.md strings table (English plus signed-off Norwegian). Failures are stated briefly and calmly, never as technical codes.
- **Done for every story:** empty, loading, error, and narrow-window states; keyboard paths; reduced motion; WCAG AA contrast, 44×44 px targets, live regions; no hard-coded colours.

## Cross-Story Dependencies

- Story 1.1 comes first: scaffold, `/api/config` (including `google_enabled`), the error envelope, test-mode startup and tests, `tokens.css`, and `config.toml` underpin everything.
- Story 1.2 sets up i18n, API-error rendering from `code`/`params`, and the frontend test conventions every later screen reuses.
- Story 1.3 creates `profiles`, `after-sign-in`, verification, `mailer.py`, and `supabase_auth.py`, reused by Stories 1.5 and 1.6. Story 1.4's `user_auth` guards every data endpoint in Epics 2–7, and Story 1.6 adds the takeover step inside it. Story 1.6 also reuses the Undo message component for its notice and the Account menu avatar for the Google photo.
- Later epics extend this: Epic 2 adds Projects, landing on the last Project, and the privacy-notice acknowledgment. Epic 7 adds Settings (read-only Google name and picture, "Link Google account" with the verify-first rule, resend verification, change password), account deletion via `supabase_auth.py`, and the completed bilingual interface.
